## §1. 측정 트리거 정량 기준 (4축 표)

### §1.1 4축 정의

| 축 | 지표 | 임계 | 측정 도구 | 판정 우선도 |
|----|------|------|----------|------------|
| **T1 호출 빈도** | 단일 메서드 호출 / frame | **> 10,000 / frame** (16.6ms 기준 = 600,000 calls/sec) | Profiler CPU Hierarchy `Self ms` + Calls 컬럼 | High |
| **T2 GC alloc** | Mono allocation / sec | **> 1 KB / sec** (5초 평균) **또는** Gen0 GC > **5회 / min** | Profiler Memory Module `GC Allocated In Frame` | High |
| **T3 FPS drop** | frame time 95-percentile | **> 16.6 ms** (60fps 기준) — Editor Standalone 동시 측정 | Profiler CPU `PlayerLoop` total + frame chart | Mid |
| **T4 Heap fragmentation** | Mono heap 사용량 | **Reserved > 50 MB** **또는** Reserved/Used 비율 **> 30%** | Memory Profiler 패키지 `Mono Heap` 분석 | Low |

### §1.2 판정 규칙 (조합)

```
판정 = High  : T1 충족 + T2 충족 (동시)
판정 = Mid   : T3 단독 충족 (T1·T2 미충족)
판정 = Low   : T4 단독 충족 (Sp03 이월 검토)
판정 = None  : 모두 미충족 (변환 불필요, 현재 코드 유지)
```

- **High** = `dots-platform` 즉시 호출, 변환 PR 분기 (Sp02 W2 또는 Sp03 W1 합류)
- **Mid** = code-lead 우선 알고리즘 / 캐싱으로 해결 시도. 1차 시도 실패 시 dots-platform 호출
- **Low** = Sp03 IdleTicker 합류 시점에 함께 재측정. Sp02 W2 단독 변환 금지
- **None** = 이번 PR 머지 OK, 다음 PR로 진행

### §1.3 임계값 근거

- **T1 = 10K / frame**: 단일 유저 / 60슬롯 / 60fps 기준. 60 × 60 = 3,600 calls/sec. 10K/frame = 600K calls/sec 는 **170배 마진**. 위반 시 무한루프 / 매프레임 전체 SO 스캔 의심.
- **T2 = 1 KB/sec**: 모바일 디바이스 Mono heap 압박 + Gen0 GC 빈도 기준. 캐릭터 MVP 완료 시점 기준 idle 시 ~ 200 B/sec 측정 (참고치).
- **T3 = 16.6 ms (95p)**: 60fps 약속. Mid 판정으로 두는 이유 = 단일 PR로 frame budget 위반은 알고리즘 문제일 가능성이 높음 (DOTS 변환 효과보다 큰 문제).
- **T4 = Reserved 50 MB / 30%**: Sp02 시점 누적 메모리 가벼움 (캐릭터 MVP 4종 + SO 카탈로그 ~10MB 예상). Low 판정 = 메모리 단독 폭증은 라이브 빌드 직전 문제, Sp02 시점 우선순위 낮음.

## §2. 측정 도구 + Sp02 W2 워크플로우

### §2.1 주 도구 = Unity Profiler (CPU / Memory / Rendering 3 모듈)

- **CPU Module**: Hierarchy 뷰 + Timeline 뷰. T1 / T3 측정.
  - Deep Profile **OFF** (overhead 5~10x). Standalone 빌드 측정 시 사전 OFF 확인.
  - Editor 측정 결과는 모바일 실측 대비 **2~3배 비관적** 추정. Editor 통과 = 모바일 통과 가정 (안전 마진).
- **Memory Module**: Simple 뷰 + Detailed 뷰. T2 / T4 측정.
  - `GC Allocated In Frame` 컬럼 = T2 직접 지표.
  - `Mono Heap` Reserved / Used = T4 직접 지표.
- **Rendering Module**: Sp02 W2 범위 외 (UI 미구현, 렌더 콜 변동 없음). 측정 생략.

### §2.2 보조 = Unity Memory Profiler 패키지

- **패키지명**: `com.unity.memoryprofiler`
- **현재 상태**: `Unity6/Packages/manifest.json` 미포함 추정 (확인 필요, Sp02 W2 D-2 이전 점검).
- **추가 필요성**: T4 (heap fragmentation) 정밀 측정 시. **Sp02 W2 시점 0건 예상** → 추가 결정 보류.
- **결정 보류 사유**: 패키지 추가 = code-lead 영역 (`Unity6/Packages/manifest.json` 수정). 본격 필요 시점 = Sp06+ 무한던전 1만 mob 검증 시. Sp02 W2 단계에서는 기본 Profiler Memory Module 로 충분.

### §2.3 Frame Debugger = Sp02 범위 외

- 렌더 분석 도구. UI / 셰이더 작업 (한지우 영역) 시 사용. Sp02 W2 = 데이터 / 런타임 PR 만이라 호출 0회 예상.

### §2.4 워크플로우 4단계 (PR 머지 전 표준 절차)

```
Step 1. PR 머지 직전 (code-lead) 또는 직후 (dots-platform 사후 검증)
Step 2. Unity Editor → Play Mode → Profiler 활성화 (Window > Analysis > Profiler)
Step 3. 30초 실행 (idle 10초 + 스폰 / 입력 / Spend 호출 10초 + idle 10초)
Step 4. CPU Hierarchy → Self ms 내림차순 → Top 5 메서드 캡처 (스크린샷 + 수치 기록)
       Memory Module → GC Allocated In Frame 5초 평균 + Mono Heap Reserved 캡처
       T1~T4 각 축 충족 여부 판정 (§1.2 규칙)
       판정 = High / Mid → PR 코멘트에 측정값 + 판정 + 후속 조치 명시
       판정 = None → PR 머지 OK
```

### §3.2 핵심 게이트 = W6-T04 (BuildSummary 1Hz vs 매프레임 호출 차단)

**리스크**:
- `PrestigeCalculator.SummarizeChannel(slots, channel, catalog)` 는 60 슬롯 × 6 stat field 누적 = **순회 60회 + 곱셈 60회 / 호출**.
- UI 갱신 코드가 매프레임 호출 시 = 60 × 60fps = **3,600 calls/sec** (T1 임계 60K / sec 의 6%, 단독으로는 안전).
- 그러나 `BuildSummary` 가 `readonly struct` 반환 = stack 할당이지만, 호출자가 `var summary = ...` 로 복사 후 매프레임 비교 시 **struct copy overhead** + LINQ 사용 시 **enumerator boxing** 위험.

**code-lead 사전 검토 1h 권장 사항** (dots-platform → code-lead 인수인계):
1. `BuildSummary` 호출 트리거 = **이벤트 기반만 허용** (`OnSlotChanged` / `OnPpChanged` 발화 시만 재계산). Update() 내 매프레임 호출 **금지**.
2. UI 레이어가 `BuildSummary` 결과를 **캐싱** (`_lastSummary` 필드). 이벤트 발화 전까지 캐시 사용.
3. `SummarizeChannel` 내부 `slots.Where(s => s.channel == channel)` 같은 LINQ 사용 **금지** (enumerator alloc 매 호출 16~32 B). 명시적 `for` 루프.
4. `BuildSummary` 필드는 Sp02 W1 game-designer 확정 stat key 집합 (예: AtkPct, CritRate, DropPct, ...) 만 포함. Sp03 Stat 시스템 확정 후 1차 동결 (Sp02 W2 시점 6 필드 추정).

**측정 스크립트 (Sp02 W2 D-2, 2026-05-29 권장)**:

## §4. DOTS Blob 변환 후보 평가 (4건)

### §4.1 후보 1: `DropRateTableSO` Dictionary 60엔트리

- **위치**: `Assets/_Project/Scripts/Data/DropRateTableSO.cs` (Sp01 W2 머지)
- **구조**: `Dictionary<DropRateKey, float>` 60 엔트리 (5 bucket × 2 mobKind × 6 grade)
- **호출 빈도 추정**: `LootRoller.RollGrade(floor, mob, rng)` → `GetDropRate` 6회 (등급별) × 분당 몬스터 처치 수 ~ 30 = **180 calls/min ≈ 3 calls/sec**. T1 임계의 **0.0005%**.
- **GC alloc**: 0 (`readonly struct DropRateKey` + `IEquatable<>` 구현 → boxing 없음)
- **판정**: **Low → 유지** (None 판정)
- **Sp02 W2 변환 결정**: ❌ 변환 불필요
- **재측정 시점**: **Sp06+ 무한던전 1만 mob/frame 시뮬 시점** (이때 호출 빈도 1만 × 6 = 60K calls/frame = T1 임계 6배 초과 가능 → DOTS Blob 강력 후보)

### §4.2 후보 2: `AffixPoolSO` List 6 엔트리 (Sp02 W2) → 36 엔트리 (Sp04)

- **위치**: `Assets/_Project/Scripts/Data/AffixPoolSO.cs` (Sp01 W2 머지, Sp04 36행 확장)
- **구조**: Sp02 W2 시점 = `List<AffixSkeletonRow>` 6 엔트리. Sp04 시점 = `List<AffixValueEntry>` 36 엔트리 추가 (35 어픽스 × ~1 분포)
- **호출 빈도 추정 (Sp02 W2)**: 어픽스 시스템 Sp04 도입 전이라 **0 calls/sec** (코드 미실행)
- **호출 빈도 추정 (Sp04)**: `AffixRoller.Roll(grade)` → 36 엔트리 중 grade 필터 + weighted pick → 분당 장비 드롭 ~ 10 = **10 calls/sec × 36 순회 = 360 lookups/sec**. T1 임계의 **0.06%**.
- **판정 (Sp02 W2)**: **Low → 유지** (호출 0)
- **판정 (Sp04 36행 시점)**: **재측정 필요**. 임계 미달 예상이지만 Sp04 머지 시 dots-platform 1회 측정 (30분).
- **Sp02 W2 변환 결정**: ❌ 변환 불필요

### §4.3 후보 3: `PrestigeItemCatalogSO` List 30 엔트리

- **위치**: `Assets/_Project/Scripts/Data/PrestigeItemCatalogSO.cs` (Sp02 W2 신설, W6-T02 PR)
- **구조**: `List<PrestigeItemRow>` 30 엔트리 + `Dictionary<ushort, int> _byItemId` 30 엔트리 (OnEnable lazy build)
- **호출 빈도 추정**: `PrestigeCalculator.CalculateBonus(in PrestigeItemRow row, int level)` 호출 시 row lookup 1회. `BuildSummary` 내부 60 슬롯 순회 = **60 lookups / SummarizeChannel 호출**. SummarizeChannel = 이벤트 기반 ~ 10 calls/sec → **600 lookups/sec**. T1 임계의 **0.1%**.
- **GC alloc**: 0 (Dictionary lookup, 모든 필드 value type)
- **판정**: **Low → 유지** (None 판정)
- **Sp02 W2 변환 결정**: ❌ 변환 불필요
- **재측정 시점**: 변경 사유 없음 (30 엔트리 고정)

### §4.4 후보 4: `PlayerPrestigeState._slots` List 60 (Sp02 W2 핵심)

- **위치**: `Assets/_Project/Scripts/Runtime/Prestige/PlayerPrestigeState.cs` (Sp02 W2 신설, W6-T03 PR)
- **구조**: `List<PrestigeSlot>` 최대 60 엔트리 (read-write hot path)
- **호출 빈도 추정 (Sp02 W2)**: `Spend` ~ 분당 1회 (유저 입력 의존), `SummarizeChannel` 내부 순회 60회 × 10 calls/sec = 600 lookups/sec. **T1 임계의 0.1%**.
- **호출 빈도 추정 (Sp06 Follower / 멀티 캐릭터 도입 시)**: 캐릭터 N명 × 60 슬롯 × 10 calls/sec = N × 600. N=10 시 6,000 lookups/sec, N=100 시 60,000 lookups/sec → **T1 임계 도달**.
- **GC alloc 위험**:
  - `_slots = new List<PrestigeSlot>()` capacity 미지정 시 List 내부 array 재할당 (4 → 8 → 16 → ...). 60까지 도달 시 6회 재할당 = **수십 KB alloc 1회성** (시작 시 한 번이라 T2 임계 영향 미미).
  - **권고 (W6-T03 사전 검토 항목)**: `_slots = new List<PrestigeSlot>(60)` capacity 명시.
- **판정 (Sp02 W2)**: **Mid 조건부 → 유지** (capacity 명시 권고 시 None)
- **판정 (Sp06+ Follower / 멀티 캐릭터)**: **High 가능성** → DOTS `IComponentData` + `DynamicBuffer<PrestigePointSlot>` 전환 후보 1순위
- **Sp02 W2 변환 결정**: ❌ 변환 불필요 (capacity 명시만)

## §5. 호출 절차 (트리거 충족 시 5단계)

### §5.1 Step 1 = code-lead 측정 보고

- PR 코멘트에 다음 4종 첨부:
  1. Profiler CPU Hierarchy 스크린샷 (Top 5 Self ms)
  2. Profiler Memory `GC Allocated In Frame` 5초 평균 스크린샷
  3. T1 ~ T4 각 축 수치 + 판정 (예: `T1 = 12,000 / frame ✅ High`)
  4. 의심 메서드 / 호출 경로 (call graph)

### §5.2 Step 2 = PD 결정 (dots-platform 호출 승인)

- code-lead 측정 보고 → PR 머지 차단 + PD에게 에스컬레이션
- PD 결정: dots-platform 호출 승인 / 보류 (다른 우선순위) / 알고리즘 시도 우선
- 결정 SLA: **24h 이내** (Sp02 W2 압축 일정, 결정 지연 시 dots-platform 자체 판단으로 측정 재현 1h 진행 + PD 사후 보고)

### §5.3 Step 3 = dots-platform 호출 (측정 재현 1~2h)

- code-lead 환경 동기화 (브랜치 / Unity 버전 / 패키지 버전)
- 동일 측정 재현 (§2.4 워크플로우 4단계)
- 재현 실패 시 = 환경 차이 분석 → code-lead와 핸드오프
- 재현 성공 시 = Step 4 진행

### §5.4 Step 4 = 변환 의사결정 (4지선다)

| 옵션 | 적용 조건 | 비용 | 효과 |
|------|----------|------|------|
| **(a) Blob 전환** | T1 ≫ 임계 + 데이터 read-only + 60 엔트리 초과 | 8~16h | 캐시 친화 + GC 0 |
| **(b) 캐싱** | 이벤트 기반 갱신 가능 + 결과 재사용 빈도 높음 | 2~4h | 호출 빈도 90% 절감 |
| **(c) 알고리즘** | 순회 / 정렬 / LINQ 남용 패턴 | 1~3h | O(N) → O(log N) 또는 enumerator 제거 |
| **(d) no-op** | 측정 오류 / 환경 차이 / 임계 재산정 합의 | 0h | PR 머지 OK |

**기본 선호 순서**: (d) → (c) → (b) → (a). DOTS 변환은 **마지막 수단**.

### §5.5 Step 5 = PR 분리 + 머지 권한

- DOTS 변환 PR 브랜치명: `feat/dots-blob-<asset>` (예: `feat/dots-blob-prestige-slots`)
- **dots-platform 단독 머지 권한 X** — code-lead 리뷰 필수 + PM 일정 합의 (Sp02 W2 압축 일정에 끼울지 Sp03 W1 으로 미룰지)
- 머지 후 sketch 문서 (`designs/sprint-02-w2-prestige-tech-sketch.md`) **갱신 의무** = dots-platform 책임. 메모리 항목 신규 등록 (`project_dots_blob_<asset>_decision.md`).
