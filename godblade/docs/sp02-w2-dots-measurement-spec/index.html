§1.2 판정 규칙 (조합)

판정 = High  : T1 충족 + T2 충족 (동시)
판정 = Mid   : T3 단독 충족 (T1·T2 미충족)
판정 = Low   : T4 단독 충족 (Sp03 이월 검토)
판정 = None  : 모두 미충족 (변환 불필요, 현재 코드 유지)
  • High = dots-platform 즉시 호출, 변환 PR 분기 (Sp02 W2 또는 Sp03 W1 합류)
  • Mid = code-lead 우선 알고리즘 / 캐싱으로 해결 시도. 1차 시도 실패 시 dots-platform 호출
  • Low = Sp03 IdleTicker 합류 시점에 함께 재측정. Sp02 W2 단독 변환 금지
  • None = 이번 PR 머지 OK, 다음 PR로 진행

§1.3 임계값 근거

  • T1 = 10K / frame: 단일 유저 / 60슬롯 / 60fps 기준. 60 × 60 = 3,600 calls/sec. 10K/frame = 600K calls/sec 는 170배 마진. 위반 시 무한루프 / 매프레임 전체 SO 스캔 의심.
  • T2 = 1 KB/sec: 모바일 디바이스 Mono heap 압박 + Gen0 GC 빈도 기준. 캐릭터 MVP 완료 시점 기준 idle 시 ~ 200 B/sec 측정 (참고치).
  • T3 = 16.6 ms (95p): 60fps 약속. Mid 판정으로 두는 이유 = 단일 PR로 frame budget 위반은 알고리즘 문제일 가능성이 높음 (DOTS 변환 효과보다 큰 문제).
  • T4 = Reserved 50 MB / 30%: Sp02 시점 누적 메모리 가벼움 (캐릭터 MVP 4종 + SO 카탈로그 ~10MB 예상). Low 판정 = 메모리 단독 폭증은 라이브 빌드 직전 문제, Sp02 시점 우선순위 낮음.

§2. 측정 도구 + Sp02 W2 워크플로우

§2.1 주 도구 = Unity Profiler (CPU / Memory / Rendering 3 모듈)

  • CPU Module: Hierarchy 뷰 + Timeline 뷰. T1 / T3 측정.
  • Deep Profile OFF (overhead 5~10x). Standalone 빌드 측정 시 사전 OFF 확인.
  • Editor 측정 결과는 모바일 실측 대비 2~3배 비관적 추정. Editor 통과 = 모바일 통과 가정 (안전 마진).
  • Memory Module: Simple 뷰 + Detailed 뷰. T2 / T4 측정.
  • GC Allocated In Frame 컬럼 = T2 직접 지표.
  • Mono Heap Reserved / Used = T4 직접 지표.
  • Rendering Module: Sp02 W2 범위 외 (UI 미구현, 렌더 콜 변동 없음). 측정 생략.

§2.2 보조 = Unity Memory Profiler 패키지

  • 패키지명: com.unity.memoryprofiler
  • 현재 상태: Unity6/Packages/manifest.json 미포함 추정 (확인 필요, Sp02 W2 D-2 이전 점검).
  • 추가 필요성: T4 (heap fragmentation) 정밀 측정 시. Sp02 W2 시점 0건 예상 → 추가 결정 보류.
  • 결정 보류 사유: 패키지 추가 = code-lead 영역 (Unity6/Packages/manifest.json 수정). 본격 필요 시점 = Sp06+ 무한던전 1만 mob 검증 시. Sp02 W2 단계에서는 기본 Profiler Memory Module 로 충분.

§2.3 Frame Debugger = Sp02 범위 외

  • 렌더 분석 도구. UI / 셰이더 작업 (한지우 영역) 시 사용. Sp02 W2 = 데이터 / 런타임 PR 만이라 호출 0회 예상.

§2.4 워크플로우 4단계 (PR 머지 전 표준 절차)

Step 1. PR 머지 직전 (code-lead) 또는 직후 (dots-platform 사후 검증)

       판정 = High / Mid → PR 코멘트에 측정값 + 판정 + 후속 조치 명시

§3.2 핵심 게이트 = W6-T04 (BuildSummary 1Hz vs 매프레임 호출 차단)

리스크:

  • PrestigeCalculator.SummarizeChannel(slots, channel, catalog) 는 60 슬롯 × 6 stat field 누적 = 순회 60회 + 곱셈 60회 / 호출.
  • UI 갱신 코드가 매프레임 호출 시 = 60 × 60fps = 3,600 calls/sec (T1 임계 60K / sec 의 6%, 단독으로는 안전).
  • 그러나 BuildSummary 가 readonly struct 반환 = stack 할당이지만, 호출자가 var summary = ... 로 복사 후 매프레임 비교 시 struct copy overhead + LINQ 사용 시 enumerator boxing 위험.

code-lead 사전 검토 1h 권장 사항 (dots-platform → code-lead 인수인계):

  1. BuildSummary 호출 트리거 = 이벤트 기반만 허용 (OnSlotChanged / OnPpChanged 발화 시만 재계산). Update() 내 매프레임 호출 금지.
  2. UI 레이어가 BuildSummary 결과를 캐싱 (_lastSummary 필드). 이벤트 발화 전까지 캐시 사용.
  3. SummarizeChannel 내부 slots.Where(s => s.channel == channel) 같은 LINQ 사용 금지 (enumerator alloc 매 호출 16~32 B). 명시적 for 루프.
  4. BuildSummary 필드는 Sp02 W1 game-designer 확정 stat key 집합 (예: AtkPct, CritRate, DropPct, ...) 만 포함. Sp03 Stat 시스템 확정 후 1차 동결 (Sp02 W2 시점 6 필드 추정).

§4. DOTS Blob 변환 후보 평가 (4건)

§4.1 후보 1: DropRateTableSO Dictionary 60엔트리

  • 위치: Assets/_Project/Scripts/Data/DropRateTableSO.cs (Sp01 W2 머지)
  • 구조: Dictionary<DropRateKey, float> 60 엔트리 (5 bucket × 2 mobKind × 6 grade)
  • 호출 빈도 추정: LootRoller.RollGrade(floor, mob, rng) → GetDropRate 6회 (등급별) × 분당 몬스터 처치 수 ~ 30 = 180 calls/min ≈ 3 calls/sec. T1 임계의 0.0005%.
  • GC alloc: 0 (readonly struct DropRateKey + IEquatable<> 구현 → boxing 없음)
  • 판정: Low → 유지 (None 판정)
  • Sp02 W2 변환 결정: ❌ 변환 불필요
  • 재측정 시점: Sp06+ 무한던전 1만 mob/frame 시뮬 시점 (이때 호출 빈도 1만 × 6 = 60K calls/frame = T1 임계 6배 초과 가능 → DOTS Blob 강력 후보)

§4.2 후보 2: AffixPoolSO List 6 엔트리 (Sp02 W2) → 36 엔트리 (Sp04)

  • 판정 (Sp06+ Follower / 멀티 캐릭터): High 가능성 → DOTS IComponentData + DynamicBuffer<PrestigePointSlot> 전환 후보 1순위
  • Sp02 W2 변환 결정: ❌ 변환 불필요 (capacity 명시만)
  • 재측정 시점: Sp06 Follower 결정 시점 (Sp09 W1 재검토 분기, 로드맵 §1 참조). 멀티 캐릭터 도입 시점.
