0. TL;DR (PD 1분)

  • 핵심 질문: 오프라인 10시간 후 복귀한 유저에게 "드롭 + 마일스톤 + PP" 를 어떻게 계산해 돌려줄 것인가.
  • 권장 전략: 옵션 C (하이브리드) — 구간 집계(평균 처치율 × 경과시간) + 마지막 1시간만 이벤트 리플레이. 드롭 표현력과 성능의 현실적 타협점.
  • 틱 주기: 온라인 방치 = 1초 고정 IdleTicker.Update() 누산. 오프라인 = 앱 포커스 복귀 시 1회 Catch-up 계산.
  • DateTime 신뢰: Sprint 03 로컬 전용 구간에선 로컬 DateTime.UtcNow 전제 + 역전 가드만. 본격 서버 검증은 Phase 5 Firebase 도입 후.
  • 아키텍처: GodBlade.Runtime.Idle 서브 네임스페이스. IdleTicker (MonoBehaviour, 앱 수명) + IdleRewardCalculator (순수 C# static) + IdleSaveService (JSON).
  • Sprint 02 W2 OnIdleReward 훅의 유일한 발화자 = IdleTicker.FlushCatchUp().
  • Open Question 5개 (§6). Sprint 03 TodoWrite 10건 W1/W2 각 5 (§7). 리스크 3건 (§8). 체크 11개 (§9).

1. 방치 시스템 요구사항 정의

1.1 온라인 방치 vs 오프라인 방치

구분정의범위처리 경로
온라인 방치앱 실행 중 + 포커스 보유 + 유저 입력 없음로비·스테이지 화면에서 자동전투 루프가 계속 도는 상태IdleTicker.Update() 매 1초 틱 누산
오프라인 방치앱 종료 / iOS 백그라운드 Suspended / 시스템 강제종료 후마지막 저장 시각 ↔ 재진입 시각 사이 경과 전부앱 재진입 시 FlushCatchUp() 1회 일괄 계산
포커스 잃은 상태 (회색지대)알림바 내림 / 카카오톡 전환 / 화면 잠금 등 — 앱은 살아있지만 Application.isFocused == falseOS 별 동작 차이 큼 (iOS 백그라운드 30초 후 Suspend, Android는 상대적 관대)방어 설계: 포커스 잃는 순간도 오프라인 간주 (마지막 틱 시각 스탬프 저장 → 복귀 시 Catch-up)

운영 원칙: "온라인 틱 vs 오프라인 Catch-up" 을 동일한 계산기(IdleRewardCalculator)로 처리. 온라인은 elapsedSec=1 을 매초 호출, 오프라인은 elapsedSec=Δ 를 1회 호출. 수식 두 벌 운영 금지.

1.2 틱 주기 트레이드오프

주기장점단점권장도
매 프레임즉시성 최대모바일 배터리·발열 유해, 60fps × 60초 = 초당 60회 드롭 롤❌
매 1초체감 즉시성 유지 + 초당 드롭 롤 1회로 예측 가능백그라운드 60fps 가정 시에도 오버헤드 적음✅ 기본값
매 5~10초저전력, CPU spike 최소드롭 애니메이션 체감 둔화Sprint 04+ 저사양 디바이스 옵션
이벤트 기반계산 최소몬스터 킬 이벤트 원천이 사라짐 (방치 특성상 자동 소환 사이클 유지가 본질)❌

결정: 매 1초 IdleTicker MonoBehaviour 에서 Update() + 내부 accumulator deltaTimeFloat 누산 → 1.0f 넘을 때만 1틱 발화. InvokeRepeating(1f) 는 Time.timeScale 변화 시 중단 이슈 + 게임 일시정지 통합 어려움으로 비권장.

1.3 "몇 시간 만에 돌아왔을 때" 계산 방식

  • 입력: elapsedSec, maxFloor, prestigeBonus(IdleRateMul), idleCapHours (프레스티지 아이템 #25 IdleCapHoursFlat — FlatStat 별도 경로 via PrestigeCalculator.GetIdleCapHours(state)) <!-- D8 검증 2026-04-21 반영 -->
  • 출력: IdleRewardBundle { kills: List<KillEvent>, gold: long, exp: long, ppGained: long, milestonesReached: List<int> }
  • 세부 전략은 §2 3옵션 비교에서 결정.

1.4 Unity 6 시간 API 검토

API용도 적합성주의
DateTime.UtcNow오프라인 경과 계산의 유일한 신뢰 지점 (로컬 범위 내)시계 조작 취약, 역전 가드 필수 (§3)
Time.realtimeSinceStartup온라인 세션 내부 경과앱 재시작 시 0 리셋 → 오프라인 계산에 부적합
Time.deltaTime온라인 틱 누산Time.timeScale=0 일시정지에 영향받음 → Time.unscaledDeltaTime 권장
Application.focusChanged (event)포커스 진입·이탈 감지iOS 백그라운드 Suspension 시점엔 발화 안될 수 있음
OnApplicationPause(bool) MonoBehaviour 콜백true=백그라운드 진입 / false=포커스 복귀핵심 훅. Catch-up 계산 + 저장 flush 타이밍
OnApplicationQuit앱 종료 직전Android·iOS에서 호출 보장 약함 → OnApplicationPause 중복 저장 권장

결정:

  • 온라인 틱 누산 = Time.unscaledDeltaTime (일시정지 영향 회피)
  • 경과 시간 측정 = DateTime.UtcNow - lastTickUtc (초 단위 차)
  • 백그라운드 진입 시점 = OnApplicationPause(true) 에서 마지막 틱 시각 저장
  • 포커스 복귀 시점 = OnApplicationPause(false) 에서 Catch-up 호출

2. 오프라인 보상 계산 전략 — 3개 옵션 비교

2.1 공통 입력

inputs:
  elapsedSec       (long)              // DateTime 차 (cap 적용 후)
  maxFloor         (int)               // 현재 최고 도달층
  dropTable        (DropRateTableSO)   // Sprint 01 W2 자산
  milestoneCatalog (MilestoneRewardCatalogSO)
  prestigeBonus    (PrestigeCalculator.BuildSummary — Sprint 02 W2 자산)
  rngSeed          (uint)              // 결정론 재현을 위한 시드

공통 제약:

  • idleCapHours (프레스티지 #24, 기본 8h Lv당 +1h, 소프트캡 Lv5 → 13h 상한 영역) 초과분은 드롭.
  • 드롭 버킷 Lookup은 Sprint 01 W2 Dictionary<(floorBucket, mobKind, grade), float> 재사용 — 신규 Lookup 구조 없음.

2.2 옵션 A — 이벤트 리플레이 (초당 시뮬)

for sec in 0..elapsedSec:
  if sec % killsPerSec == 0:
    KillEvent k = SimulateKill(currentFloor, rng)
    dropTable.RollDrops(k, rng)   // 등급 drop 굴림
    if ShouldAutoAdvanceFloor(...):
      floor++
      CheckMilestone(floor)
  accumulator.Add(k)
  • 장점: 온라인 틱 코드 재활용 가능 (동일 로직). 드롭 분포 완전 정확. "방치 로그" UI에 시간대별 이벤트 표현 가능.
  • 단점: 10h × 3600sec × 초당 1킬 = 36,000 회 RollDrops — 수백 ms ~ 1s+ CPU 스파이크. 24h 캡 시 86,400회 — 체감 프리즈 위험.
  • 성능 측정 필요: Unity 6 모바일 Mono에서 Dictionary Lookup + System.Random.NextDouble 기준, 36,000회 ≈ 100~300ms 예상 (중급 기기). 허용 범위지만 여유 없음.

2.3 옵션 B — 집계 공식 (평균 처치율 × 경과시간)

killsTotal   = killsPerSec × elapsedSec
goldTotal    = killsTotal × avgGoldPerKill(currentFloor) × prestigeBonus.GoldMul
expTotal     = killsTotal × avgExpPerKill(currentFloor) × prestigeBonus.ExpMul
drops        = ExpectedDrops(killsTotal, dropTable, currentFloor, mobKind)  // 확률 × 횟수
ppGained     = floor((elapsedSec / 3600) × maxFloor × 0.05 × prestigeBonus.IdleRateMul)
  • 장점: O(1) 계산. 10시간·24시간·48시간 모두 동일 1ms.
  • 단점:
  • 드롭 표현력 상실 — "레어 1개, 에픽 0개" 같은 정수 결과가 평균 개수(예: 0.37개)로 표현됨 → 반올림 or 확률 추첨 한번으로 해결해야.
  • 마일스톤 "방치 중 돌파" 시퀀스를 잡기 어려움 (언제 100→101→102 도달?) — 별도 FloorProgressEstimator 로 수식화 필요.
  • "방치 동안 층 자동 진행 허용" 여부 (§6 Q3) 에 따라 복잡도 극심 차이.

2.4 옵션 C — 하이브리드 (구간 샘플링 + 마지막 구간 리플레이) 권장

cappedSec = min(elapsedSec, idleCapHours × 3600)

// Phase 1: 첫 구간 = 공식으로 집계 (cappedSec - 3600 초)
if cappedSec > 3600:
  bulkSec   = cappedSec - 3600
  bulkBundle = AggregateFormula(bulkSec, dropTable, milestoneCatalog, prestigeBonus)

// Phase 2: 마지막 1시간 = 이벤트 리플레이 (최대 3600회)
tailSec      = min(cappedSec, 3600)
tailBundle   = ReplayEvents(tailSec, dropTable, ..., rng)

// 합산
finalBundle = bulkBundle + tailBundle
  • 장점:
  • 리플레이 횟수 상한 3,600회 고정 — 10h든 24h든 성능 동일.
  • 마지막 구간은 이벤트 로그로 "방치 보고서" UI 표현 가능 ("최근 1시간 동안 에픽 2개 획득" 등).
  • Bulk 구간은 집계 수식 → 긴 방치에도 즉시 응답.
  • 단점:
  • 구현 복잡도 옵션 A·B 합산 → 테스트 커버리지 2배.
  • 마일스톤 돌파 타이밍은 여전히 추정 (Phase 1 집계에서 "이 1시간 구간 동안 105→108층" 식 추정).
  • 적합성: 1인 파트타임 + 모바일 타겟 + 방치형 핵심 체험 ("돌아왔는데 짜잔!") 모두 만족. Sprint 03 권장.

2.5 각 옵션의 드롭·마일스톤·PP 처리 차이

항목옵션 A (Replay)옵션 B (Formula)옵션 C (Hybrid)
드롭매 초 RollDrops 호출, 실제 아이템 결정론확률 × 횟수의 기대값 → 정수 반올림 or 1회 Poisson 추첨Bulk = 기대값, Tail = 실 Roll
마일스톤층 진행 함수 따라 정확히 돌파 시점 포착추정 공식으로 "Δsec 동안 몇 층 진행" → 배치 발화Bulk=추정, Tail=실시간. 경계 층 누락 가능
PP (OnIdleReward 훅)초당 maxStage × 0.05 / 3600 누적elapsedSec / 3600 × maxStage × 0.05 공식 1회Bulk+Tail 합산 후 단일 OnIdleReward 1회 발화
로그 UI 표현력최상 (시계열 그래프 가능)최하 (요약 숫자만)중 (최근 1h만 상세)

2.6 권장 — 옵션 C (하이브리드)

근거:

  1. 1인 파트타임 관점에서 옵션 B는 단순 구현이지만 "방치 보고서" UI에 콘텐츠가 없어 방치형 게임 체감이 죽는다.
  2. 옵션 A는 24h 캡 시 86,400회 루프 — 저사양 기기 리스크 + 복귀 프리즈.
  3. 옵션 C는 리플레이 횟수 상한 고정(3,600) + 드롭 표현력 유지. 구현 복잡도는 Sprint 03 11~15h 예산에서 수용 가능.
  4. Sprint 04+ 저사양 디바이스 옵션으로 "tail=0" (완전 옵션 B) 전환이 쉬움 (파라미터 하나로 토글).

3. 타임스탬프 관리 & 치팅 방지

3.1 로컬 DateTime 신뢰 가능한가

  • 모바일 유저는 설정 > 일반 > 날짜 및 시간 을 임의로 변경 가능 → 8시간 → 24시간 조작 시도 가능.
  • Sprint 03 범위에선 Firebase Timestamp 동기 불가 (Phase 5+). 따라서 로컬 시계 전적 신뢰 + 보수적 이상 탐지.

3.2 Sprint 03 로컬 방어 체크리스트

이상 케이스감지 방법대응
lastTickUtc > DateTime.UtcNow (역전)elapsed < 0 이면 로그 + elapsed = 0 처리보상 0. 토스트 "시간 확인"
elapsed > 30일 (비정상 장기)캡 idleCapHours 가 자연 상한. 단 의도적 리셋 감지 위해 elapsed > 30일 이면 Warn캡 적용 후 정상 처리 (리셋은 Phase 5+ 서버 도입 전까지 유저 권리 범위)
기기 재부팅 후 시각 변경검출 불가 (로컬만으로는 한계)Sprint 03 범위 외 — Phase 5 Firebase 서버 시각 검증에 위임
시간대 변경DateTime.UtcNow 는 시간대 독립 → 영향 없음OK

3.3 치팅 허용 입장

  • 현재 방침: 로컬 치팅은 부분 허용 (싱글·방치형, 글로벌 랭킹 없음). 대응은 Steam Anti-cheat + Firebase Phase 5 서버 시각 검증.
  • Sprint 03 구현은 역전 가드 1개 + 30일 Warn 1개 만. 과도한 감지 로직 금지 (UX 해침).

3.4 저장할 타임스탬프 필드

IdleSaveDto {
  int  schemaVersion      = 1
  long lastTickUtcMs      // DateTime.UtcNow.Ticks / 10000 (ms 단위)
  long lastFocusExitUtcMs // OnApplicationPause(true) 시 갱신
  int  lastKnownMaxFloor  // 오프라인 동안 층 변화 없음 가정
  uint rngSeed            // 결정론 재현
  long savedAtUtcMs       // 디버그
}

3.5 장치 재부팅 / 시간대 변경

  • DateTime.UtcNow 는 장치 재부팅 생존 (OS가 RTC 유지).
  • 시간대 변경은 UTC 기준이므로 무영향.
  • 단, 유저가 "기기 초기화 + 날짜 변경" 하면 감지 불가 → Phase 5+ 서버 시각으로 위임.

4.4 초기화 시점

  1. 게임 부팅 (Start()): IdleSaveService.Load() → _lastTickUtc 복원. 즉시 FlushCatchUp() 1회 호출 → OnIdleReward 1회 발화.
  2. 스테이지 진입: _currentMaxFloor 갱신. 틱은 계속 진행 (스테이지 전환은 IdleTicker 생명에 영향 없음).
  3. 포커스 복귀 (OnApplicationPause(false)): 현 시각 ↔ _lastTickUtc Δ 계산 → FlushCatchUp().
  4. 씬 전환: DontDestroyOnLoad 로 유지. 초기화 반복 금지.

4.5 이벤트 발화 순서 (§6 Sprint 02 W2 계약 준수)

FlushCatchUp() 내부 순서:

1. elapsed 계산 + cap 적용 + 역전 가드
2. IdleRewardCalculator.Calculate(...)  → IdleRewardBundle
3. 순서 (배치 발화):
   a. bundle.MilestonesReached.ForEach(floor => MilestoneGranter.Award(floor))   // Sprint 01 W2 채널 B
      └─ floor==100 시 PlayerPrestigeState.Unlock() 내부 연쇄 (Sprint 02 W2 계약)
      └─ floor==200 시 PrestigePpAccumulator.GrantMilestone(200) 연쇄
   b. bundle.KillsTotal / DropsCompact → 인벤토리 수령 (Sprint 04+ 인벤토리 시스템 확정 후. Sprint 03은 로그만)
   c. PrestigePpAccumulator.GrantIdleDrip(elapsed, maxFloor)
   d. OnIdleReward?.Invoke(bundle)  // 최종 집계 이벤트 — UI가 "방치 보고서" 모달로 소비
4. IdleSaveService.Save()  // lastTickUtc 갱신

불변식: OnIdleReward 발화 시점엔 Milestones·Drops·PP 모두 이미 적용된 상태. UI는 후처리 표시만.

4.6 OnIdleReward 와 PrestigePpAccumulator.GrantIdleDrip 관계

  • PP 발화자 분리:
  • GrantIdleDrip(elapsed, maxFloor) → PlayerPrestigeState.AddPermanentPp(amount) 호출 (실제 PP 적립)
  • OnIdleReward(bundle) → UI 알림용 집계 이벤트
  • 순서: 적립 먼저 (c 단계), UI 알림 나중 (d 단계). UI 가 "이번 방치로 +N PP" 표시할 때 이미 State 반영 완료.
  • 왜 분리: Sprint 02 W2 PrestigePpAccumulator 가 PP 수식 소유권 (§3.3 계산 공식). IdleTicker 는 그 호출자일 뿐. 이중 관리 금지.

8. 리스크 & 블로킹 예상 3건

8.1 모바일 OS 백그라운드 제한 (특히 iOS 30초 Suspend)

  • 증상: iOS 는 앱이 백그라운드 진입 후 약 30초 내 Suspend. 이후 Update() 정지. OnApplicationPause(true) 는 Suspend 직전 호출 보장이 약함 (Unity 버전·OS 조합 변수).
  • 리스크: 유저가 백그라운드로 돌린 후 30초 뒤 앱이 Suspend → 10분 뒤 다시 열면 OnApplicationPause(false) 가 먼저 호출됨. 이때 _lastTickUtc 가 Suspend 직전이 아니라 앱 진입 시점이면 오프라인 계산 누락.
  • 완화:
  • OnApplicationPause(true) 호출 시 즉시 IdleSaveService.Save() + lastTickUtc = DateTime.UtcNow flush.
  • OnApplicationPause(false) 는 재계산만 수행 (Save는 재진입 후 1틱 지나야 다시).
  • 추가 안전망: Update() 내부에서 1분에 1회 Save flush (1분 미만 차이면 iOS Suspend에도 큰 손실 없음).
  • Sprint 03 범위 내 해소 가능. 전담 테스트: 실제 iOS 실기 테스트는 Phase 3+ 빌드 파이프라인 가능 후 재확인 (CP-I8 체크리스트 이월).

8.2 DateTime.UtcNow 치팅 — 로컬 검증 한계

  • 증상: 유저가 시스템 시각을 +24h 조작하면 idleCapHours 기본 8h 캡을 돌파하지 못해도 "8h 치 보상 매번 재획득" 가능 (앱 재시작마다).
  • 리스크: 싱글·방치·랭킹 없음 정책상 허용 가능하지만, Steam 도입 시 업적·과금 회귀 우려.
  • 완화:
  • Sprint 03: 로컬 DateTime.UtcNow 신뢰 + 역전 가드만.
  • Sprint 05+ Firebase: ServerValue.TIMESTAMP 로 최종 검증. IdleSaveService.Load 가 서버 시각 주입받도록 시그니처 확장 준비 (Load(string accountId, DateTime? serverUtcNow = null)).
  • 현 Sprint 범위 = 로컬 방어만. PD 승인 필요 (Q에는 올리지 않음 — 기존 정책 일관).

8.3 옵션 C 리플레이 RNG 결정론 실패 시 테스트 불가능

  • 증상: System.Random 은 Next() 호출 순서가 결정론적이지만, Dictionary 순회 순서 의존 시 플랫폼·런타임 간 편차 가능.
