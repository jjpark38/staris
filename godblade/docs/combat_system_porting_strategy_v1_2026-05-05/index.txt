4:T254b,# 전투 시스템 Unity 6 포팅 전략 v1

**작성**: 정현우 (code-lead)
**일자**: 2026-05-05
**연계**: `combat_system_analysis_v1_2026-05-05.md` §7 호환성 평가
**APPROVED**: 정현우 자율 (PD 출장 복귀 시 인수)

## 1. PD 핵심 지시 (2026-05-05)

> "GodBlade 제일 중요한 건 전투 시스템. 탁월한 손맛 + 전투 이펙트 + 스킬 = 강점. 잘 분석해서 진행 중인 게임에 그대로 가져오거나 거의 비슷하게 구현."

**PD 우선순위**: A (그대로) > B (비슷하게) > C (핵심만)

## 2. 전제 조건 (현재 잠금)

- **Phase 4 (2027-04+) 본판 출시** — Steam + 모바일 (메모리 `project_phase_2_3_roadmap_v3_0.md`)
- **Sp02~05 PAUSE** (5/18~9/14) — 웹게임 우선
- **Unity Sp02 재개 9/15** — 워밍업 1주 권장 (R-V3-1)
- **200F 4.255 baseline 절대 보존** — 본 포팅 영향 0% (분석 v1 §9)
- **류재현(dots-platform)**: 무한던전 1만 시뮬 / DOTS — 별도 트랙
- **본 포팅 시점**: Phase 4 진입 (2027-04+) 또는 Sp02 W2~W4 일부 선행 가능

## 3. 3안 비교

### A안 — 그대로 가져오기 (drop-in port)

**범위**:
- `Program/Client/Assets/Scripts/Entity/` 64 파일 그대로 복사
- `Program/Client/Assets/Scripts/Camera/EodCamera.cs` 복사
- `Program/Client/Assets/Scripts/Foundation/EodMatrixTrail.cs` + Xft 라이브러리 복사
- 네임스페이스 `SnowFamily.EvilOfDarkness` 그대로 유지 (별칭 `Eod`)
- Addressables 콜백 → async/await 1건 패치
- Xft 1건 검증 (Unity 6 호환 안 되면 대체)
- 데이터 테이블 9건 (Skill / SkillEvent / SkillType / SkillLevelup / SkillLevelUseData / PassiveSkill / SuccessionSkill / OccupationSkill / GuildSkill) FlatBuffer 변환 (이미 잠금)

**비용**: 약 **120h** (3주 풀타임 / 6주 파트타임)
- Entity 64 파일 복사 + 컴파일 에러 패치 = 50h
- Xft 검증 또는 대체 = 25h
- Addressables async/await = 5h
- CSV → FlatBuffer 변환 (50h 의 일부 흡수, 추가 0h)
- 테스트 (Unit Test 80% 커버리지) = 30h
- 라이브 안정성 검증 (콤보 100 / 카메라 흔들림 4 진입점 / Matrix Trail 좌우) = 10h

**리스크**:
- (R-A-1, 중) Xft 라이브러리 Unity 6 미보증 — 대체 시 +2주
- (R-A-2, 낮) god 클래스 2건 (Combat 2499 / Skill 1794) 잔존 → 라이브 패치 회귀 위험 누적
- (R-A-3, 낮) 멀티 잔재 (PvP / 길드전 / 점령전 분기) 잔존 → dead code 정리 부채
- (R-A-4, 중) 디버그 코드 잔존 (잔상 5초 자동 발화) → **포팅 시 필수 제거**

**가능성**: **HIGH** — 코드가 견고하고 외부 의존 2건만 → 8개월 안에 가능

**손맛 보존도**: **100%** — 4중 메커니즘 (콤보/Shake/Trail/잔상) + 13 SkillEvent + 35 EventBase 그대로

**장점**:
- PD 1순위 부합
- 검증된 동작 (10년 라이브 운영 이력)
- 시간 단축 (B 안 대비 -40%)
- 손맛 0 손실

**단점**:
- 부채 (god 클래스 2건 / 멀티 분기 / 디버그 코드) 그대로
- Unity 2019 디자인 패턴 잔존 (singleton EodCamera.Get 등)

### B안 — 거의 비슷하게 재구현 (semantic port)

**범위**:
- 새 코드베이스 `Unity6/Assets/Scripts/Combat/` 신설
- 동일 동작 보존:
  - TimeEvent 패턴 100% 유지 (Skill 클래스 / List<TimeEvent>)
  - 콤보 시스템 (max 100, 3초 리셋)
  - 카메라 흔들림 4 진입점 → 단일 Camera Shake API
  - Matrix Trail 좌/우 무기 궤적
  - 잔상 복제 N개
  - 35 EventBase → 동일 35 (또는 일부 통합)
- god 클래스 분할: Combat → 4 sub / Skill → 3 sub
- 멀티 분기 제거 (싱글 only)
- 데이터 테이블 9건 그대로 (FlatBuffer)
- C# 9.0 패턴 활용 (record / pattern matching / async/await)
- DOTS 적용 평가 (정현우 영역 X, 류재현 인계 가능)

**비용**: 약 **240h** (6주 풀타임 / 12주 파트타임)
- 새 코드베이스 설계 = 30h
- TimeEvent + Skill 재구현 = 60h
- EventBase 35 재구현 = 40h
- 4중 손맛 메커니즘 재구현 + Xft 대체 = 50h
- god 클래스 분할 = 30h
- 데이터 파이프라인 (FlatBuffer) = 20h (50h 의 일부 흡수, 추가 0h)
- Unit Test = 40h (커버리지 80%)
- 라이브 안정성 검증 + 손맛 동등성 검증 (정현우 + 윤서아 협업) = 20h

**리스크**:
- (R-B-1, 높) **손맛 미세한 차이 발생 가능** — 원본 10년 튜닝 결과 재현 어려움
- (R-B-2, 중) 일정 -3개월 (A안 대비 2배)
- (R-B-3, 낮) 새 버그 도입 가능
- (R-B-4, 낮) 윤서아(game-designer) 손맛 검증 부담 증가

**가능성**: **MEDIUM** — 일정 빠듯, Phase 4 (2027-04) 안 12개월 안에 가능

**손맛 보존도**: **80~95%** — 미세 차이 가능

**장점**:
- 코드 부채 0
- C# 현대 패턴 활용
- 멀티 분기 제거로 코드 -30%
- DOTS 등 신기술 도입 가능
- god 클래스 분할로 라이브 안정성 향상

**단점**:
- 일정 +3개월
- 손맛 동등성 검증 부담
- PD 2순위 (A안 우선)

### C안 — 핵심만 포팅 (minimal viable port)

**범위**:
- 손맛 4중 메커니즘만:
  - 콤보 100 / 3초 리셋
  - 카메라 흔들림 단일 진입점
  - Matrix Trail (Xft 대체)
  - 잔상 복제
- 13 SkillEvent 중 핵심 5개:
  - CreateProjectile / ShakeCamera / MoveToNearestTarget / TeleportForward / Rotate
- 35 EventBase 중 핵심 10개:
  - DoBaseAttack / DoAttack / OnSkillUsed / OnHit / OnDamaged / OnCollideProjectile / ShakeCamera / GetSocketTransform / FindUsableSkill / GetEquipSkills
- 나머지는 Phase 4.5 (2027-10+) 점진 추가

**비용**: 약 **80h** (2주 풀타임 / 4주 파트타임)

**리스크**:
- (R-C-1, 높) **손맛 손실 30~50%** — Action 시스템 / 잔상 / Sub Skill / Push Move 누락
- (R-C-2, 중) Phase 4.5 추가 작업 +120h 누적 (총합 200h, A안 보다 +80h)

**가능성**: **HIGH** (8주 안 가능)

**손맛 보존도**: **50~70%**

**장점**:
- 빠른 출시 가능
- Phase 4 일정 여유 확보 (-1.5개월)

**단점**:
- 손맛 약화 → PD 핵심 지시 위배
- Phase 4.5 추가 작업 누적 → 결국 A 안 보다 비용 많음

## 4. 정현우 권고: **A안**

### 4.1 권고 이유

1. **PD 1순위 부합** ("그대로 가져오기" 명시)
2. **손맛 100% 보존** (10년 튜닝 자산 그대로)
3. **비용 -50% (B안 대비)** — Phase 4 일정 안전
4. **C 안 보다 총비용 -40%** (장기적 합산)
5. Xft 1건 + async/await 1건 = 2건만 패치하면 99% 동작 (분석 v1 §7)

### 4.2 A안 보완 권고 (코드 부채 헷지)

A안 그대로 가져오면 god 클래스 2건 / 디버그 코드 / 멀티 분기 부채 누적. 이를 헷지하기 위해 **A+ 보완**:

| 항목 | 작업 | 추가 비용 | 시점 |
|------|------|----------|------|
| 디버그 코드 즉시 제거 | EodEntityMatrixEffectComponent line 67~77 | 1h | 포팅 시 |
| 멀티 분기 dead code 표시 | `// TODO Sp03+ 제거` 주석 | 4h | 포팅 시 |
| god 클래스 분할 | Combat 2499 / Skill 1794 | 30h | Sp02 W2~W4 (재개 후) |
| Xft 대체 | Unity 6 TrailRenderer + Bezier | 25h | 포팅 시 |
| Unit Test 80% | 점진 도입 | 30h | 포팅 시 |

**A+ 총합**: 120h (A안) + 60h (보완) = **180h** (B안 240h 보다 -25%)

### 4.3 Sp01 W2 baseline 보존 영향

- 본 포팅 = Phase 4 (2027-04+) 진입 시 본격
- Sp01 W2 (5/11~5/17) **본 작업 0%** — Importer baseline 보존만
- Sp02 재개 (9/15+) 시 **god 클래스 분할 30h 부분 선행 가능** (워밍업 1주 후)
- 메모리 `project_sprint01_w1_results.md` 200F 4.255 + 0.12% 편차 baseline 영향 0%

### 4.4 Phase 4 일정 영향

- Phase 4 본판 출시 = 2027-04
- Sp02 재개 9/15 ~ 2027-04 = **약 19개월**
- A+ 총합 180h = 4.5주 풀타임 또는 9주 파트타임
- 19개월 중 0.5개월 (2.6%) 소요 → **여유 충분**
- Phase 4 막판 1.5개월 풀타임 또는 Phase 3 (Sp06+, 2026-09~) 분산 가능

- B 결정 시 일정 +3개월 + 손맛 미세 차이 위험
- C 결정 시 PD 핵심 지시 위배 + 장기 비용 더 큼

### D-2: Xft 라이브러리 처리 (PD 결정 후 정현우 자율)

- D-2a: Xft 그대로 + Unity 6 호환 PoC 1h (호환 시 채택)
- D-2b: Unity 6 TrailRenderer + Bezier 자체 구현 (~200 LOC, 25h)
- D-2c: Asset Store 대체 ($30~$50)
- 정현우 권고: **D-2b** (외부 의존 제거 + 라이브 안정성)

### D-3: god 클래스 분할 시점 (PD 결정 + 류재현 협업 의향 확인)

- D-3a: 포팅 동시 분할 (총 비용 180h)
- D-3b: 포팅 후 Phase 4.5 분할 (총 비용 200h, +20h)
- D-3c: 분할 안 함 (라이브 부채 누적, 비추)
- 정현우 권고: **D-3a** (포팅 1회 작업으로 통합)
