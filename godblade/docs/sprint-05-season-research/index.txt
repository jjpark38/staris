## 1. 시즌 시스템 요구사항 정의

### 1.1 시즌 개념의 최소 정의

- **시즌**: "유한 기간 동안만 유효한 병렬 진행 축 + 종료 시 일부 가치 영구화 + 다음 시즌 리셋 반복".
- 방치형 RPG + 무한던전 장르 특성상 **유저의 영속 성장(Permanent)과 시즌 성장(Seasonal)이 명확히 분리**돼 있어야 동기가 분산되지 않는다. 이 분리는 이미 Sprint 02 W2 `PpChannel : byte { Permanent, Seasonal }`로 **구현 레벨에서 예약 완료**.

### 1.2 시즌 기간 옵션 (1인 파트타임 운영 관점)

> 수치 튜닝은 game-designer 영역. 본 문서는 **엔지니어링 관점의 코스트 구조**만 제시.

| 기간 | 운영 코스트 (1인/시즌) | 컨텐츠 소비 위험 | 리더보드 경쟁성 |
|------|----------|------|-----|
| 30일 | 월 1회 리셋·이벤트 발화·검증 **8~12h/월 고정비** | 빠른 소진, 신선도↑ | 단기 러쉬 활발 |
| **60일** | 2개월 1회 **4~6h/월 아마겟비** | 중간 | 중위 |
| 90일 | 분기 1회 **2~3h/월 아마겟비** | 느린 소진, 이탈 위험 | 긴 호흡 |
| 무기한 (관리자 수동) | 이벤트 발생 시 1~2h | 자율적 | 정체성 약함 |

- **권장 엔지니어링 구조**: 기간을 **하드코딩하지 않음**. `seasonEndUtc` 를 `SeasonConfigSO` (로컬) + Firebase Remote Config 중 **우선순위 있는 단일 지점**에서 주입. PD/game-designer가 60→30→90 어느 쪽으로 바꿔도 코드 수정 없이 컨피그만 갱신.

### 1.3 시즌 시작·종료 트리거 세 경로

| 트리거 | 장점 | 단점 | Sprint 05 적합성 |
|--------|------|------|---------|
| 자동 (로컬 타이머) | 서버 無 | 시계 조작·복귀 실패 치명 | ❌ |
| 관리자 수동 | 1인 운영 유연, 긴급 종료 가능 | 유저 예측 불가 | Phase 4(개발) ✅ |
| Firebase Remote Config 기반 | 서버 권위, 일괄 전파 | Firebase 러닝커브 | Phase 5+ ✅ |

- **권장**: Phase 4(Sprint 05 초~중)는 **관리자 수동 + 디버그 메뉴**로 시작, Phase 5에서 Remote Config로 승격. 양쪽 모두 동일한 `ISeasonClock` 인터페이스 뒤에 숨기면 교체 코스트 2~3h.

### 1.4 시즌 보상 카테고리

| 카테고리 | 채널 | 영구화 정책 | 예시 |
|---------|------|-----------|------|
| Seasonal PP | `PpChannel.Seasonal` | 시즌 종료 시 50% → Permanent 전환 (Q3) | 일반 드립·보스·마일스톤 |
| MythicEssence (시즌 한정 재화) | 별도 지갑 | 시즌 종료 시 **삭제 또는 영구 이관** — §4.4 결정 필요 | Mythic 재롤/해체 보상 |
| 시즌 한정 어픽스 | 신규 TSV `seasonal_affix_pool_s<N>.tsv` | 시즌 종료 후 재롤 불가, 기존 아이템에 한해 유효 | Legendary 고정 Power 시즌 차별화 |
| 시즌 셋 효과 | 신규 `SetItemCatalogSO` | 다음 시즌 풀 교체 or 누적 | 2셋/4셋 보너스 |
| 명예의 전당 기록 | Firebase (영구) | 시즌 리더보드 top N 스냅샷 저장 | 최고 층, 완주 시간 |

### 1.5 로컬 전용 vs Firebase 필요성

- **로컬만으로 가능**: 시즌 전환, PP 마이그레이션, 시즌 보상 드롭, Mythic 재롤 — 모두 클라 권위 + 로컬 저장으로 충분 (원본 서버 전투 로직 無 결정과 일관).
- **Firebase 필요 최소 집합**:
  - `seasonEndUtc` Remote Config (시계 조작 방지)
  - 시즌 리더보드 쓰기/읽기 (글로벌 랭킹 없이는 시즌 자체의 경쟁적 의미 약함)
  - 명예의 전당 영구 스냅샷
- **Firebase 불필요**: 프레스티지 세이브 동기 (Phase 5+ 유예 유지)

## 2. `OnSeasonEnd` 이벤트 발화 전략 — 3옵션 비교

Sprint 02 W2 §6.2 신규 훅 3개 중 `OnSeasonEnd` 만 **구독자 존재 / 발화자 없음** 상태. Sprint 05에서 발화자를 어디에 둘지 결정한다.

### 2.1 옵션 A — 관리자 수동 트리거

```
UI: Debug 메뉴 "[Season] Force End Current Season" 버튼
   → SeasonController.ForceEnd() 호출
   → OnSeasonEnd 발화
   → PlayerPrestigeState.MigrateSeasonalToPermanent(0.5f)
```

- **장점**: 1인 운영 현실 완벽 부합. 버그·과부하 시 즉시 연장·단축 가능. Phase 4 개발 중 테스트 용이.
- **단점**: 유저 입장에서 불확실성. 상용 출시 시 "운영자가 맘대로 종료한다" 불만 리스크.
- **적합**: Phase 4 (Sprint 05 개발) 기본값. Phase 5 이후에도 "긴급 핸들"로 유지.
- **복구**: Migrate 실행 도중 앱 종료 시 §3.4 참조 — 이중 발화 방지 필수.

### 2.2 옵션 B — 로컬 타이머 (앱 시작 시 `DateTime.UtcNow >= seasonEndUtc` 확인)

```
SeasonController.Update() (1초 또는 앱 포커스 복귀 시):
  if (now >= seasonEndUtc && !seasonEnded) {
    OnSeasonEnd 발화
    seasonEnded = true (저장)
  }
```

- **장점**: 서버 없이 작동. 구현 단순 (`IdleTicker` 시계 로직 재활용).
- **단점**: **치팅 치명**. 유저가 시스템 시계를 2026-01-01로 되돌리면 시즌이 영원히 종료되지 않거나 반복 종료. Sprint 03 방치 시스템의 `DateTime.UtcNow` 가드는 "음수·30일 초과 경고"만 있고 "조작 자체 차단"은 못함.
- **복구**: 시즌 종료 이벤트 발화 → 앱 종료 → 시계 롤백 시 이중 발화 경로 존재. `seasonId` 별 `migrated:bool` 플래그로 방어 가능하지만 복잡도 증가.
- **권장 안 함**.

### 2.3 옵션 C — Firebase Remote Config `currentSeasonId` + `seasonEndUtc`

```
앱 시작 / 1h 주기 / 포커스 복귀 시:
  Firebase.RemoteConfig.FetchAndActivate()
  remoteSeasonId = config.currentSeasonId
  if (remoteSeasonId != localSeasonId) {
    // 서버가 시즌 넘어감 선언
    OnSeasonEnd 발화 (localSeasonId 기준 마이그)
    localSeasonId = remoteSeasonId
  }
```

- **장점**: 서버 권위 = 치팅 차단. 글로벌 일괄 전파. `seasonEndUtc` 표시(클라 카운트다운)와 실제 전환 분리 가능.
- **단점**: Firebase 첫 도입 러닝커브. `FetchAndActivate` 실패 시 fallback 전략 필요. 오프라인 장기 유저의 "서버보다 1시즌 뒤처진 상태" 처리.
- **적합**: Phase 5+ 상용 기본값.

### 2.4 권장안

| Phase | 기본 트리거 | 보조 |
|-------|-----------|------|
| Phase 4 (Sprint 05 개발) | **옵션 A 관리자 수동** | 디버그 메뉴 버튼 + 콘솔 커맨드 |
| Phase 5+ (상용) | **옵션 C Firebase Remote Config** | 옵션 A 긴급 핸들 상시 유지 |
| 어디에도 | **옵션 B 로컬 타이머 배제** | 치팅 리스크 대비 수익 없음 |

- 양 옵션 공통 추상화: `ISeasonClock` 인터페이스 → `ManualSeasonClock` / `RemoteConfigSeasonClock` 구현 교체. Sprint 05는 Manual만 실구현, Remote는 Phase 5 과제로 등록.

### 2.5 `MigrateSeasonalToPermanent(0.5f)` 발화 타이밍·복구·롤백

- **발화 타이밍**: `OnSeasonEnd` → `SeasonEndModal` UI 표시 → "확인" → Migrate 호출. 모달 없이 자동 Migrate도 기술적으로 가능하지만 유저 혼란(PP 갑자기 반토막) 방지 위해 **모달 필수**.
- **복구 지점 3단계**:
  1. `OnSeasonEnd` 발화 직후 `prestige.v1.json` 백업 (`.bak` + `_season<N>_pre_migrate`).
  2. Migrate 실행 → 성공 시 `migrated=true` 플래그 저장.
  3. 실패 또는 앱 종료 시 다음 실행에서 `.bak` 로부터 복구.
- **이중 발화 방지**: `PrestigeSaveDto.lastMigratedSeasonId` 필드 신설 → `schemaVersion=1 → 2` 마이그레이션 필요(§3).

## 3. `MigrateSeasonalToPermanent` 활성화 & 데이터 흐름

### 3.1 현재 상태 (Sprint 02 W2 APPROVED)

```csharp
// GodBlade.Runtime.Prestige / PlayerPrestigeState.cs (이미 시그니처 존재)
public void MigrateSeasonalToPermanent(float retainRatio); // 구독자 없음 = no-op
```

- 호출자 없음. 테스트(`PrestigeSeasonMigrationTests.T5`)에서만 직접 호출하여 불변식 검증.

### 3.2 Sprint 05 신규 부수 효과

Sprint 02 W2 `PlayerPrestigeState.MigrateSeasonalToPermanent` 본문(의사코드) 외 신규 필요:

1. **저장 플래그**: `lastMigratedSeasonId` 기록 (이중 발화 방지)
2. **백업 파일 생성**: `prestige.v1.json.bak` + `prestige_season<N>_pre_migrate.json`
3. **UI 이벤트**: `OnPpChanged` 2회(Permanent 증가 / Seasonal→0) + **신규 `OnSeasonEndMigrationCompleted(seasonId, oldSeasonalPp, retainRatio, convertedPp)` 이벤트 1건**
4. **누적 방치 처리**: 시즌 종료 시점에 `IdleTicker.FlushCatchUp()` **강제 1회 실행** → 마지막 방치 PP가 Seasonal 에 반영된 후 Migrate. 순서 뒤집히면 방치 PP가 Permanent 로 직행.
5. **마일스톤 스냅샷**: `MilestoneGranter` 의 현 시즌 maxFloor 을 리더보드 제출 후 리셋 (시즌별 기록 분리)

### 3.3 50% 전환 로직 & 라운딩 정책

Sprint 02 W2 §4.3 의사코드를 확장:

```
MigrateSeasonalToPermanent(retainRatio=0.5f):
  // Step 0: 방치 누산 강제 flush (신규)
  IdleTicker.Instance?.FlushCatchUp(forceImmediate: true)

  // Step 1: Seasonal 슬롯 전부 회수
  seasonalInvested = Σ slot.investedPp where channel=Seasonal
  totalPool = SeasonalPp + seasonalInvested   // unspent + invested 모두
  RemoveAll(s => s.channel == Seasonal)

  // Step 2: retainRatio 적용 — 라운딩 정책 결정 필요 (Open Q6)
  converted = LongMulFloor(totalPool, retainRatio)  // (long * numerator / denominator) 정수 연산
  PermanentPp += converted
  SeasonalPp = 0

  // Step 3: 플래그 저장 + 백업
  lastMigratedSeasonId = currentSeasonId
  PrestigeSaveService.Save(this, accountId)

  // Step 4: 이벤트 발화
  OnPpChanged(Permanent, PermanentPp)
  OnPpChanged(Seasonal, 0)
  OnSeasonEndMigrationCompleted(seasonId, totalPool, retainRatio, converted)
```

- **라운딩 정책 3안** (Open Q6에서 결정):
  - (a) `Floor` — 유저 불리, 대규모 PP 유실 가능 (100 PP → 50 / 101 PP → 50, 1 PP 손실)
  - (b) `Round` — 통계적 중립, 유저·시스템 50:50
  - (c) `Ceiling` — 유저 유리, PP 인플레 약간 가중
- 권장: **(b) Round, 소수 첫째자리에서**. 단, 정수 연산 구현 `(long * 50) / 100` → 500 기준 정확한 50% 보장.

## 5. 시즌 리더보드 아키텍처

### 5.1 저장소 3옵션

| 저장소 | 쓰기 | 읽기 | 영속성 | 치팅 방어 |

### 5.2 시즌 종료 후 "명예의 전당"

- **정책**: 시즌 종료 시 리더보드 top 100 스냅샷 → `hall_of_fame/season_<N>/` 컬렉션에 **불변 복제** (Firestore rules: `allow read; allow create if admin; allow update,delete = false`).
- 영구 보존. 2027년 출시 5년 후에도 "2026 S1 Top 1: DobbyCat" 조회 가능.
- 앱 종료 중 시즌 전환 시에도 누락 안 됨 — 서버 Cloud Function 으로 실행.

### 9.2 Firebase 첫 도입 러닝커브 + 지연

- **리스크**: Firebase SDK 통합 3h 예산은 낙관적. Android `google-services.json` / iOS `GoogleService-Info.plist` 설정, Firestore Security Rules 작성, 인증 흐름 디버깅 — 실제 8~12h 소요 가능. 메모리 `feedback_codelead_review_compile_verify.md` 패턴 재현 (정적 리뷰 통과 후 실제 컴파일 회귀).
- **완화**: Sprint 05 W1 T4 를 "Firebase SDK **통합까지만**"으로 제한. Firestore 실제 쓰기·읽기는 T5 스켈레톤만. Phase 5 초 별도 스프린트 가능성 열어둠.
- **블로킹 알람**: T4 4h 초과 시 PM 에스컬레이션 → T5·T10 Firebase 부분 Sprint 06 이월.
