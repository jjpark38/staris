1. 시즌 시스템 요구사항 정의

1.1 시즌 개념의 최소 정의

  • 시즌: "유한 기간 동안만 유효한 병렬 진행 축 + 종료 시 일부 가치 영구화 + 다음 시즌 리셋 반복".
  • 방치형 RPG + 무한던전 장르 특성상 유저의 영속 성장(Permanent)과 시즌 성장(Seasonal)이 명확히 분리돼 있어야 동기가 분산되지 않는다. 이 분리는 이미 Sprint 02 W2 PpChannel : byte { Permanent, Seasonal }로 구현 레벨에서 예약 완료.

1.2 시즌 기간 옵션 (1인 파트타임 운영 관점)

수치 튜닝은 game-designer 영역. 본 문서는 엔지니어링 관점의 코스트 구조만 제시.

1.5 로컬 전용 vs Firebase 필요성

  • 로컬만으로 가능: 시즌 전환, PP 마이그레이션, 시즌 보상 드롭, Mythic 재롤 — 모두 클라 권위 + 로컬 저장으로 충분 (원본 서버 전투 로직 無 결정과 일관).
  • Firebase 필요 최소 집합:
    • seasonEndUtc Remote Config (시계 조작 방지)
    • 시즌 리더보드 쓰기/읽기 (글로벌 랭킹 없이는 시즌 자체의 경쟁적 의미 약함)
    • 명예의 전당 영구 스냅샷
  • Firebase 불필요: 프레스티지 세이브 동기 (Phase 5+ 유예 유지)

2. OnSeasonEnd 이벤트 발화 전략 — 3옵션 비교

Sprint 02 W2 §6.2 신규 훅 3개 중 OnSeasonEnd 만 구독자 존재 / 발화자 없음 상태. Sprint 05에서 발화자를 어디에 둘지 결정한다.

2.1 옵션 A — 관리자 수동 트리거

UI: Debug 메뉴 "[Season] Force End Current Season" 버튼
   → SeasonController.ForceEnd() 호출
   → OnSeasonEnd 발화
   → PlayerPrestigeState.MigrateSeasonalToPermanent(0.5f)
  • 장점: 1인 운영 현실 완벽 부합. 버그·과부하 시 즉시 연장·단축 가능. Phase 4 개발 중 테스트 용이.
  • 단점: 유저 입장에서 불확실성. 상용 출시 시 "운영자가 맘대로 종료한다" 불만 리스크.
  • 적합: Phase 4 (Sprint 05 개발) 기본값. Phase 5 이후에도 "긴급 핸들"로 유지.
  • 복구: Migrate 실행 도중 앱 종료 시 §3.4 참조 — 이중 발화 방지 필수.

2.2 옵션 B — 로컬 타이머 (앱 시작 시 DateTime.UtcNow >= seasonEndUtc 확인)

SeasonController.Update() (1초 또는 앱 포커스 복귀 시):
  if (now >= seasonEndUtc && !seasonEnded) {
    OnSeasonEnd 발화
    seasonEnded = true (저장)
  }
  • 장점: 서버 없이 작동. 구현 단순 (IdleTicker 시계 로직 재활용).
  • 단점: 치팅 치명. 유저가 시스템 시계를 2026-01-01로 되돌리면 시즌이 영원히 종료되지 않거나 반복 종료. Sprint 03 방치 시스템의 DateTime.UtcNow 가드는 "음수·30일 초과 경고"만 있고 "조작 자체 차단"은 못함.
  • 복구: 시즌 종료 이벤트 발화 → 앱 종료 → 시계 롤백 시 이중 발화 경로 존재. seasonId 별 migrated:bool 플래그로 방어 가능하지만 복잡도 증가.
  • 권장 안 함.

2.3 옵션 C — Firebase Remote Config currentSeasonId + seasonEndUtc

앱 시작 / 1h 주기 / 포커스 복귀 시:
  Firebase.RemoteConfig.FetchAndActivate()
  remoteSeasonId = config.currentSeasonId
  if (remoteSeasonId != localSeasonId) {
    // 서버가 시즌 넘어감 선언
    OnSeasonEnd 발화 (localSeasonId 기준 마이그)
    localSeasonId = remoteSeasonId
  }
  • 장점: 서버 권위 = 치팅 차단. 글로벌 일괄 전파. seasonEndUtc 표시(클라 카운트다운)와 실제 전환 분리 가능.
  • 단점: Firebase 첫 도입 러닝커브. FetchAndActivate 실패 시 fallback 전략 필요. 오프라인 장기 유저의 "서버보다 1시즌 뒤처진 상태" 처리.
  • 적합: Phase 5+ 상용 기본값.

3.3 50% 전환 로직 & 라운딩 정책

Sprint 02 W2 §4.3 의사코드를 확장:

MigrateSeasonalToPermanent(retainRatio=0.5f):
  // Step 0: 방치 누산 강제 flush (신규)
  IdleTicker.Instance?.FlushCatchUp(forceImmediate: true)

  // Step 1: Seasonal 슬롯 전부 회수
  seasonalInvested = Σ slot.investedPp where channel=Seasonal
  totalPool = SeasonalPp + seasonalInvested   // unspent + invested 모두
  RemoveAll(s => s.channel == Seasonal)

  // Step 2: retainRatio 적용 — 라운딩 정책 결정 필요 (Open Q6)
  converted = LongMulFloor(totalPool, retainRatio)  // (long * numerator / denominator) 정수 연산
  PermanentPp += converted
  SeasonalPp = 0

  // Step 3: 플래그 저장 + 백업
  lastMigratedSeasonId = currentSeasonId
  PrestigeSaveService.Save(this, accountId)

  // Step 4: 이벤트 발화
  OnPpChanged(Permanent, PermanentPp)
  OnPpChanged(Seasonal, 0)
  OnSeasonEndMigrationCompleted(seasonId, totalPool, retainRatio, converted)
