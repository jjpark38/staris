### §0.2 최상위 리스크 3건

1. **R-DR-07 [High · 하이브리드 계산 결정론 실패]** — #03 (Bulk 집계) + #04 (Tail 3,600초 리플레이) 가 동일 입력(`elapsedSec`, `maxFloor`, `rngSeed`)에 대해 **에디터 빌드 vs 모바일 IL2CPP 빌드 사이에서 다른 드롭 결과** 생성 가능. 근본 원인: `DropRateTableSO._lookup` Dictionary 순회가 Sp01 W2에서 `(floorBucket, mobKind, grade)` 복합키 구조 — Dictionary 순회 순서는 .NET Mono vs IL2CPP 사이에서 비결정적. CP-M19는 "리플레이 iteration 은 `rows` List 사용" 명시하나 **실제 구현 시 습관적으로 `_lookup` 순회 유혹**. 테스트(#08) Edit Mode에서 Green이어도 모바일 빌드에서 Red. Sp03 범위 내 실기 테스트 불가 → **Edit Mode 테스트에서 List 인덱스 순 강제 assert 필수**.

2. **R-DR-08 [High · `OnApplicationPause` Unity 6 + 모바일 플랫폼 차이]** — 설계 §1.4 / §8.1 / CP-I8 명시된 위험. iOS 30초 Suspend 이후 `OnApplicationPause(true)` 호출 보장 약함. **Unity 에디터 Play Mode 에서 `OnApplicationPause` 는 포커스 전환(`Application.isFocused`) 시에만 발화 — 실제 모바일 Suspend 시나리오 재현 불가**. Smoke Test(#09)는 "시뮬 모드로 10h elapsed 입력" 이므로 `OnApplicationPause` 실호출 경로 미검증. Sp03 범위에서 **모바일 실기 테스트 불가 확정** → CP-M22 "실기 검증 Phase 3+ 이월" PR 본문 명시. 드라이런 추가 권고: Editor Play Mode 수동 시나리오 1개 정의 — "Play 중 `Application.Quit()` → 재Play → `FlushCatchUp` 로그 확인".

Sp02 W2 회고(2026-05-31) 시점에 `GetIdleCapHours` 미구현이면 Sp03 #03 하이브리드 `cappedSec = min(elapsed, GetIdleCapHours(state) × 3600)` 호출부 작성 불가. **사전 완화 A1 (킥오프 D-1)**: Sp02 W2 PR 목록에서 `GetIdleCapHours` 헬퍼 머지 확인 필수. 미머지 시 Sp03 킥오프 오전 긴급 선행 (0.5h, #06 이전 삽입).
   > **[2026-04-21 설계 스펙 해소 — 부분 FP]** Sp02 W1 R-DR-06 FP 교훈 적용, 4건 전수 설계 문서 실측 완료: (1) `GetIdleCapHours(in PlayerPrestigeState)` = [d8-stat-key-validation-2026-04-21.md:169](../designs/d8-stat-key-validation-2026-04-21.md#L169) `public static int` 시그니처 명시 ✅ (2) `BuildSummary` 4필드(IdleRateMul/GoldMul/ExpMul/DropMul) = [sprint-02-w2-prestige-tech-sketch.md:230·235](sprint-02-w2-prestige-tech-sketch.md#L230) `SummarizeChannel` + `public readonly struct BuildSummary` 명시 ✅ (3) `AddPermanentPp/AddSeasonalPp(long)` = [sprint-02-w2-prestige-tech-sketch.md:193-194](sprint-02-w2-prestige-tech-sketch.md#L193) public void 2건 ✅ (4) `PrestigePpAccumulator.GrantIdleDrip + OnIdleReward 구독` = [sprint-02-w2-prestige-tech-sketch.md:381·386·390](sprint-02-w2-prestige-tech-sketch.md#L381) §6.3 스케치 + `public sealed class` ✅. **부분 FP 확정**: 설계 스펙 누락 우려 = False Positive (전 4건 APPROVED 문서에 시그니처 존재). **잔여 위험 유지**: 2026-05-31 Sp02 W2 실 PR 머지 여부 확인 = A1 여전히 필수(설계 → 구현 drift 가능성). 리스크 재분류 **Medium-High → Low-Medium**. #06 긴급 선행 가능성 거의 0.

## §13. 하이브리드 계산 수리적 검증 (엣지 케이스 4종)

> 설계 §2.4 옵션 C 하이브리드가 실제 디아블로 감성 ("돌아왔는데 짜잔!") 과 일치하는지 예상 체감 시뮬. 실측 불가 — 드라이런 수리 검증만.

### §13.1 엣지 케이스 1 — 0초 방치 (Just Launched)

- 입력: `elapsedSec=0, maxFloor=100, idleCapHours=24`
- 기대: `bundle.ElapsedSec=0, PpGained=0, DropsCompact=[], MilestonesReached=[]`
- 위험: Calculator 가 `cappedSec=0` 반환 후 Bulk/Tail 둘 다 skip — `IdleRewardBundle.Empty` 반환해야 함
- **수리 검증**: `cappedSec > 3600` false → bulkSec=0. `tailSec = cappedSec = 0` → ReplayEvents 루프 0회. 정상.
- **체감**: 앱 첫 실행 or 재시작 직후 — 아무 보상 없어도 자연스러움. UX OK.

### §13.2 엣지 케이스 2 — 1시간 직전 방치 (3,599초)

- 입력: `elapsedSec=3599, maxFloor=100`
- 기대: Tail 전체 (3,599초 리플레이), Bulk=0
- 위험: `cappedSec > 3600` false → **Bulk 로직 skip → Tail만 실행**. 정상 동작
- **수리 검증**: `bulkSec = 0, tailSec = 3599`. Tail ReplayEvents 3599회. 성능 OK (< 300ms).
- **체감**: "1시간 자리 비운 후 돌아옴" — 드롭 리플레이 표현력 최대 (Sp04 "방치 보고서" UI 기대). Sp03는 Debug.Log만.

### §13.3 엣지 케이스 3 — 34h 캡 초과 방치 (48h 실제)

- 입력: `elapsedSec=172800 (48h), idleCapHours=34 (Lv5 투자 가정)`
- 기대: `cappedSec = 34*3600 = 122400`. bulkSec=118800, tailSec=3600
- 위험: 48h→34h 잘라냄 = 14h 손실. 유저 불만 가능. 캡 UX 핵심
- **수리 검증**: `cappedSec = min(172800, 34*3600) = 122400`. `bulkSec = 122400-3600 = 118800`. `tailSec = 3600`. Bulk 33시간 집계 + Tail 1시간 리플레이. PP = floor(34 × 100 × 0.05 × 1.0) = 170 PP.
- **체감**: 2일 자리 비운 후 돌아와 PP 170 + 드롭 (Tail 1시간분) — 34h 캡 체감 가능. PR 본문 "Sp04 광고 48h 확장" TODO.

### §13.4 엣지 케이스 4 — 앱 종료 직후 재시작 (0.5초)

- 입력: `elapsedSec ~= 0.5s (long 반올림 0)`
- 기대: `bundle.ElapsedSec = 0`
- 위험: DateTime 차이 ms 단위 → long 초 변환 시 소수점 절삭. 0초 반환 → 엣지 케이스 1과 동일
- **수리 검증**: `(long)((DateTime.UtcNow - _lastTickUtc).TotalSeconds) = 0`. OK.
- **체감**: 앱 강제종료 → 재시작 — 보상 0 자연스러움. 단 OnApplicationPause 이후 재진입이 너무 빠를 때 Save/Load 경합 주의 (CP-M22 Safe Flush).

### §13.5 하이브리드 체감 검증 결론

- 4 엣지 전부 정상 동작 예상. Sp04 "방치 보고서" UI 콘텐츠 표현력은 Tail 3,600초 리플레이에서 나옴 — 옵션 C 하이브리드 선택 근거 (설계 §2.6) 재확인
- **리스크**: 캡 34h = 긴 방치(1일+) 유저 "손실 체감". Sp04 광고 48h 확장 도입 전까지 감내 — PD 인지 필요

## §14. OnApplicationPause 플랫폼 리스크 상세 (R-DR-08 심화)

### §14.1 플랫폼별 발화 타이밍

| 플랫폼 | `OnApplicationPause(true)` 발화 | `OnApplicationPause(false)` 발화 | 보장도 |
|--------|--------------------------------|----------------------------------|--------|
| Unity 6 Editor (Play Mode) | Editor 포커스 잃을 때 (다른 창 클릭) | Editor 포커스 복귀 | **부분** — 실제 백그라운드 아님 |
| Android | Home 버튼 / 앱 전환 / 화면 잠금 | 앱 재진입 | **보장** — API level 차이 존재, Unity 6는 상대 안정 |
| iOS | Home 버튼 직후 (< 1초) | 앱 재진입 | **부분 보장** — Suspend 진입(30초 후) 시점엔 미발화 |
| Steam (PC Windows/Linux) | 포커스 잃을 때 | 포커스 복귀 | **약함** — OS별 차이, Alt-Tab 미발화 가능 |

### §14.2 iOS Suspend 시나리오 분석

```
T+0   : 유저 Home 버튼 누름
T+0.5s: OnApplicationPause(true) 발화 → _lastTickUtc = DateTime.UtcNow 저장 (성공 예상)
T+30s : iOS 앱 Suspend (프로세스 동결)
T+10min: 유저 앱 재진입
T+10min+ε: OnApplicationPause(false) 발화 (iOS Resume)
         → FlushCatchUp() 호출, elapsed = 10min 계산 정상
```

**문제 시나리오**: T+30s 이전에 iOS 가 앱을 **즉시 Kill** (메모리 압박) → OnApplicationPause(true) 미발화 → _lastTickUtc 미저장 → 재시작 시 Save 파일의 이전 값 사용, 30초 ~ 10분 격차 누락 가능성.

**완화**: 
1. `Update()` 내 1분 주기 Safe Flush (CP-M22) — 1분 이내 격차만 허용
2. `OnApplicationQuit` 이중 저장 (설계 §1.4) — iOS는 호출 보장 약함, Android는 상대 강함

### §14.3 Android 플랫폼 안정성

- Unity 6 Android는 백그라운드 진입 시 OnApplicationPause(true) 보장
- 단 "최근 앱" 리스트에서 스와이프 Kill 시 OnApplicationQuit도 미발화 여지
- 완화: OnApplicationPause(true) 시 즉시 Save (설계 §1.4 + §8.1 "이중 저장")

### §14.4 Steam (PC) 플랫폼

- Alt-Tab / Windows 잠금 시 OnApplicationPause 발화 불안정
- 대안: `Application.focusChanged` 이벤트 병행 구독 가능
- Sp03 범위: OnApplicationPause 만 사용. focusChanged 는 Phase 3+ 이월

### §14.5 Sp03 범위 제약 명시

- **Sp03 PR 본문 필수 문구**: "OnApplicationPause 실기 검증은 Phase 3+ 빌드 파이프라인 도입 후 이월. Editor Play Mode 포커스 전환 시나리오만 검증." (A5 사전 완화)

- **실기 테스트**: iOS Kill, Android 백그라운드 30분, Steam Alt-Tab 등 Phase 3+ 이월

## §15. IdleTicker MonoBehaviour Singleton 리스크 상세

### §15.1 singleton 패턴 취약점 3건

| 취약점 | 발생 조건 | 대응 |
|--------|-----------|------|
| **중복 생성** | 씬 전환 시 DontDestroyOnLoad 누적 — 다른 씬에 IdleTicker 프리팹 배치 시 2개 이상 | Awake 가드: `if (_instance != null && _instance != this) { Destroy(gameObject); return; }` |
| **OnDestroy 순서** | Unity 6 Play Mode 종료 시 MonoBehaviour OnDestroy 호출 순서 불확정. `_instance == this` 체크 없으면 다른 ticker OnDestroy 후 `_instance` null 설정 → 첫 ticker가 `_instance == null` 오해 | `if (_instance == this) _instance = null;` 가드 |
| **Play Mode 첫 프레임 경합** | Start() 전 Awake 에서 `_lastTickUtc` 미초기화 → Update() 첫 호출 시 NullReference | Awake에서 `_lastTickUtc = DateTime.UtcNow` 초기화 (Start에서 Load 이후 덮어쓰기) |

### §15.2 DontDestroyOnLoad 누적

- IdleTicker GameObject를 어느 씬에 배치하는가? — Sp03 범위에선 **부트스트랩 씬 (현재 없음)** 전제. Sp04+ 씬 구조 확정 후 프리팹 배치 재검토
- 임시 방안: `IdleTicker` 를 static 메서드로 초기화 — `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterSceneLoad)]` → GameObject 자동 생성
- **권장**: Sp03는 `RuntimeInitializeOnLoadMethod` 로 1회 자동 생성 + DontDestroyOnLoad. 프리팹 의존성 Zero

### §15.3 씬 전환 시 연속성

- Sp03 범위에선 씬 전환 없음 (Smoke Test 단일 씬). Sp04+ 로비 ↔ 스테이지 씬 전환 도입 시 재검증 필요
- 완화: `_instance` static 필드 + DontDestroyOnLoad 로 씬 독립. 씬 전환 시 OnApplicationPause 미발화 확인

### §15.4 OnDestroy 순서 리스크

- Play Mode 종료 시 `OnDestroy` 호출 → `IdleSaveService.Save` 시도 — 이미 `_instance=null` 이면 `_prestige` 필드 접근 실패 가능
- 완화: OnDestroy에서 `try/catch` + `_instance != null` 가드 먼저
